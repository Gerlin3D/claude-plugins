Прогони серию шагов из `$ARGUMENTS` через workflow плагина pipeline.

1. Разбери аргументы. Флаги: `--commit` — коммитить каждый успешно принятый шаг (сообщение коммита = заголовок шага, на английском); `--stop-on-blocked` — останавливать серию на первом шаге с блокирующим решением (по умолчанию такой шаг пропускается, серия идёт дальше). Остальное — список шагов: одна строка или один нумерованный пункт = один шаг. Если пользователь ссылается на раздел документа плана (например «§6.1–6.3 из docs/REFACTORING_CANDIDATES.md»), прочитай документ и разверни ссылку в конкретные шаги, по одному на пункт плана, сохранив формулировки и ссылки на файлы из плана. Если в тексте шага есть уже принятые решения — положи их в `decisions`.
   Гранулярность: один шаг = один коммит, который архитектор может спроектировать за ограниченное число ходов. Пункт плана, который трогает несколько слоёв сразу, дели на под-шаги в порядке зависимости: сначала схема/миграция/клиент, потом каждый сервис-потребитель отдельно, потом UI. Два зеркальных сервиса (например DV360 и Google Ads) — два шага, не один. Лучше восемь маленьких шагов, чем три больших.
2. Для каждого шага сформируй `{ "title": "<короткий английский заголовок, годится для коммита>", "task": "<полная формулировка задачи со ссылкой на пункт плана>", "decisions": "<если есть>" }`. Покажи пользователю получившийся список шагов одной строкой на шаг и запусти workflow — подтверждения не жди, пользователь уже запустил команду.
3. Вызови инструмент Workflow с `name: "pipeline:batch"` и `args: { "steps": [...], "commit": <true|false>, "stopOnBlocked": <true|false>, "runScriptPath": "${CLAUDE_PLUGIN_ROOT}/workflows/run.js" }`. Если workflow по имени не находится — `scriptPath: "${CLAUDE_PLUGIN_ROOT}/workflows/batch.js"` с теми же args. Сам агентов не запускай и код не пиши.
4. По результату отчитайся по шагам в порядке выполнения:
   - `approved` — что изменено (`result.filesTouched`), сколько находок подтверждено/опровергнуто по раундам, проверки с результатом как есть, закоммичен ли шаг;
   - `approved_with_failing_checks` / `unresolved_findings` — что именно упало или осталось (`result.checks`, `result.unresolved`), серия на этом остановлена;
   - `blocked` — вопросы архитектора (`blockingDecisions`) списком, чтобы пользователь ответил; эти шаги можно перезапустить отдельно через `/pipeline:implement` с ответами;
   - `notRun` — какие шаги не дошли до запуска и почему (`stopReason`).
   Проверку с `fail` или `not_run` пройденной не называть. Если серия шла без `--commit`, напомни, что изменения всех шагов лежат в рабочем дереве одним куском.
5. Без `--commit` ничего не коммить и никогда не пушить.
