Проведи `$ARGUMENTS` через передачу «проектирование → реализация».

1. Прочитай задачу и текущее состояние репозитория. Если область незнакомая — сначала делегируй read-only карту агенту `pipeline:code-mapper`.
2. Делегируй проектирование агенту `pipeline:feature-architect`, передав задачу и отчёт mapper'а, если он был.
3. Если бриф содержит блокирующее решение (модель данных, границы слоёв, интеграции, поведение фоновых джоб, API-контракты) — остановись и спроси пользователя. Реализацию не начинать.
4. Утверждённый бриф передай агенту `pipeline:feature-implementer` без изменений. Попроси применить релевантные скиллы проекта и вернуть изменённые файлы, тесты и оставшиеся риски.
5. Проверь результат и `git diff`; запусти проверки, которые требует репозиторий для такого изменения. Не заявляй, что проверка прошла, если она не запускалась в этой сессии.

Передача должна оставаться узкой: архитектор решает, **что** менять, исполнитель — только рутинные детали кодирования, нужные для выполнения брифа.

Правки коммитить не нужно, если пользователь не просил.
